# 알고리즘 분해 트리 — 시간표 도메인 (확정)

> **상태 (2026-05-17 확정)**: 시간표 추천 도메인의 알고리즘 분해 트리가 **product 방향(균형 모델, 후보 C)에 맞춰 확정**됨.
> 본 문서의 §9가 정식 내용이며, **코드 결정의 근거로 인용 가능**.
> §1~§8은 초기 LT-as-DAG 방향 탐색 자료로 **폐기 대기** (참고용으로만 유지; 새 결정의 근거로 인용하지 말 것).
> 다음 단계: `architecture.md` §4.1로 §9를 흡수하면 본 파일은 완전 폐기.

---

## 1. 한 줄 아이디어

`algorithms.md`에 정리된 기본 알고리즘들을 **리프**에 두고, 하삼각 행렬 위에서 풀고 싶은 하나의 큰 문제를 **루트**로 하는 **분해 트리**로 시스템을 구성한다. 트리 자체가 곧 LLM에 줄 설명 구조가 된다.

## 2. 핵심 제약 (이게 안 지켜지면 아이디어 자체가 무의미해진다)

- **리프부터 정하지 않는다.** "4개를 쓰자 → 트리를 만들자" 순서로 가면 부모 노드가 단순 디스패치가 되어 트리의 가치가 사라진다.
  반대로 가야 한다: **하삼각 도메인 위의 한 문제를 정의 → 자연스러운 분해 → 그 결과로 4개 이상의 리프가 떨어진다.**
- **부모 노드는 실제 합성 일을 해야 한다.** 자식 결과를 (a) 필터링, (b) 합치기, (c) 변환, (d) 다음 자식 입력으로 가공 — 이 네 가지 중 하나라도 해야 트리에 있을 자격이 있다. 단순 호출만 하는 부모는 트리에서 뺀다.
- **트리 깊이는 2~3단계.** LT 규모에서 4단계 이상은 거의 항상 부풀린 트리다. 리프 6~7개에 깊이 2~3이 현실적 상한.

## 3. 잘 맞는 이유 (본 저장소 구조 기준)

- `architecture.md` §3.2 원칙과 정합: **리프 = `app/libs/<algo>.py`의 순수 함수**, **내부 노드 = `app/libs/composer.py`의 합성 모듈**, **라우트는 루트만 호출**. 의존 방향이 자연스럽게 유지된다.
- `architecture.md` §4의 LLM 데이터 흐름과 궁합이 좋다. 트리 구조가 곧 `llm_context.build()`에 넣을 설명 골격이 된다 — "이 문제를 이렇게 쪼갰고, 이 자리에는 왜 이 알고리즘을 골랐다".
- 평가 측면에서 "왜 굳이 4개를 다 썼냐"는 질문에 대한 답이 **부모-자식 관계 자체에** 박힌다.

## 4. 우려 / 미해결 항목

1. **`product.md`가 비어 있어 정당화 근거가 없다.**
   교육적 설명이 우선이면 트리는 결정적으로 좋고, 수치 정답이 우선이면 트리는 오버엔지니어링이다. §4 우선순위 한 줄이 먼저 정해져야 한다.
2. **노드 간 입출력 계약 = base 변경.**
   각 노드의 입력·출력 타입은 `app/schemas/`로 굳혀야 하며, 이는 `base/CLAUDE.md` §1에 따라 base 변경이다. 코드 작업 전에 `architecture.md`에 새 절(예: "§4.1 알고리즘 분해 트리")을 추가해야 한다.
3. **추상화 극장(abstraction theater) 위험.**
   부모가 자식을 단순 호출만 한다면 트리는 곧 리스트와 동치가 된다. 설계 단계에서 각 부모의 "합성 책임"을 글로 적어두고 그게 비면 그 노드는 삭제한다.

## 5. [폐기 대기] 예시 트리 스케치 — LT-as-DAG 방향 (초기 탐색)

> ⚠️ 이 절은 timetable 방향 채택 전의 초기 탐색 자료입니다. 본 절의 예시는 §9로 대체되었습니다.
> 참고용으로 유지하되, **새 결정의 근거로 인용하지 마세요.** `architecture.md` §4.1 흡수 시 본 절은 함께 폐기됩니다.

루트 문제를 다음과 같이 잡았다고 가정한다.

> "**하삼각 행렬을 DAG의 인접행렬로 해석한 뒤, 그 위에서 의미 있는 분석을 수행하고 학습용으로 설명한다.**"

```
[루트] LT 행렬 분석 파이프라인
 ├── [노드 A] 입력 정규화·정렬
 │    └── 리프1: Merge Sort 또는 Heap Sort
 │         (행/열의 가중치 기준 정렬, 안정 정렬 필요 시 Merge)
 ├── [노드 B] 그래프 해석
 │    ├── 리프2: Floyd-Warshall  (LT를 DAG로 보고 모든 쌍 최단 경로)
 │    └── 리프3: Dijkstra        (특정 시작점, B의 결과와 비교)
 └── [노드 C] 경로 비교·요약
      ├── 리프4: LCS             (두 경로의 공통 부분 구조 추출)
      └── 리프5: 이진 탐색         (정렬된 결과에서 임계값 위치 탐색)
```

각 부모의 합성 책임:

- **노드 A**: 정렬 결과를 노드 B의 그래프 입력 형태(인접 리스트/행렬)로 변환한다. 단순 정렬 호출이 아니라 "정렬 + 그래프 자료구조 빌드"가 일이다.
- **노드 B**: Floyd-Warshall과 Dijkstra의 결과를 같은 페어 키로 정렬·정렬해 노드 C가 비교 가능한 형태로 만든다.
- **노드 C**: 두 경로 결과를 LCS로 비교하고, 그 결과를 이진 탐색으로 검색 가능한 인덱스로 만들어 최종 응답에 싣는다.

리프 수: 5개(요건 4개 충족). 카테고리 커버: 정렬 / 그래프-DP / 그래프-탐욕 / DP / 탐색 — `algorithms.md`의 5개 묶음 중 4개를 자연스럽게 횡단한다.

## 6. 대안 방향 (참고용)

- **방향 B**: 하삼각 = "의존성 행렬"로 해석 → 위상 정렬 + DP(0-1 배낭 또는 행렬 경로) + MST(크루스칼) + 이진 탐색.
- **방향 C**: 하삼각 = "분할 정복의 부분 영역 표현" → Merge Sort + Closest Pair + Matrix Path + LCS.

어느 방향을 갈지는 `product.md` 한 줄 요약이 결정한다.

## 7. 진행 권고 (base 작업자 관점)

1. **`product.md` §1·§2·§4를 먼저 채운다.** 특히 §4에서 "교육적 설명 vs 수치 정답"의 순위가 박혀야 한다.
2. 루트 문제 한 문장을 사용자와 합의한다 ("하삼각을 X로 해석해 Y를 계산하고 Z 형태로 설명한다" 형식).
3. 트리 초안을 **글로** 먼저 그린다 — 노드별 입출력 · 합성 책임 · 해당 리프 알고리즘 · 그 알고리즘을 고른 한 줄 근거.
4. 합의되면 `architecture.md`에 새 절을 추가하고 `app/schemas/`에 노드 간 계약을 정의한다(§2.4 절차: 승인 → 영역 progress.md → architecture.md → 코드 → base/progress.md).
5. 트리가 굳어진 뒤 각 리프 구현은 `server/tasks.md`로, 설명 자료는 `llm-include/tasks.md`로 카드 분배. **트리 자체는 base, 리프는 영역.**

## 9. 시간표 도메인 상세 트리 — 확정 (locked)

> **상태 (2026-05-17 확정)**: 본 절의 트리가 알고리즘 구조의 **정식 계획**으로 확정.
> 책임 기반 3분할(옵션 1: A 가능성 / B 가치 / C 선택)과 각 자식 노드의 추상 수준·핵심 알고리즘 자리는 **모두 잠금**.
> 변동 여지가 있는 항목은 §9.9 표로 분리되어 있으며, 이들의 결정은 `architecture.md` §4.1 흡수 또는 `app/schemas/` 정의 시점에 일어남.
> §5·§6의 LT-as-DAG 방향은 본 확정으로 **폐기 대기** 상태가 되며, §9가 단독 정식 계획임.

### 9.1 루트와 첫 단계 자식 (책임 기반 3분할)

```
[루트] 최적 시간표 추천 알고리즘
 ├── [A] 가능성 분석 (Feasibility)   — "어떤 조합이 hard 제약을 통과하는가"
 ├── [B] 가치 평가 (Valuation)        — "통과한 조합이 얼마나 좋은가"
 └── [C] 선택과 비교 (Selection)      — "무엇을 어떻게 보여줄 것인가"
```

추상 수준: A·B는 좁→넓(per-course → per-pair → per-set)으로 합성, C는 넓→좁으로 풀어내림. divide-conquer-combine 형상.

### 9.2 A — 가능성 분석

질문: 어떤 강의 조합이 hard 제약을 통과하는가.

- **A-1 강의 풀 정제 (per-course)** — 해시 탐색
  사용자 명시 제외(개별·그룹) 처리, 데이터 정합성 검증, blackout 제거(걸친 슬롯이 하나라도 있으면 강의 통째 제외 — 강의는 슬롯을 쪼갤 수 없음), 필수 잠금(개별·그룹) 플래그 부착. 중복 강의 ID 검사.
- **A-2 충돌 관계 산출 (per-pair)** — 정렬, 이진 탐색
  시간 겹침·이동 시간 부족 검사(같은 날 연속 슬롯의 필요 간격 = **max(이동시간, `min_break_minutes`)** — 이동 시간은 **슬롯별 건물** 기준이며, 한 강의가 요일마다 다른 건물에서 열릴 수 있음) + **같은 `course_group_id` 공유 시 양립 불가** (분반 상호 배타). 양립 가능성 행렬 구축.
- **A-3 후보 공간 가지치기 (per-subset)** — 활동 선택, (위상 정렬)
  학점 한도 도달 가능성 검증, 필수 강의·필수 그룹 양립성 검증(그룹당 최소 1개 분반 존재), B 단계 DP가 소비할 시간 순 시퀀스 구축.

**그룹 처리 추가 자료 (Course·PV 확장)**:
- `Course.course_group_id` (Optional) — 같은 과목의 분반들을 묶는 키. 같은 값 공유 강의는 *상호 배타*.
- `Course.section`, `Course.professor` (Optional) — 표시·교수 가중치 룩업 용도.
- `PV.must_include_groups`, `PV.exclude_groups` — 그룹 단위 명시 제약.
- `PV.professor_preferences` — 교수 가중치 (B-1 가산 항).
- `TimeSlot.building` — **건물은 슬롯 단위**(요일마다 다른 건물 가능). `Course.building`은 표시·직렬화용 대표 건물 파생값(최빈 건물).

### 9.3 B — 가치 평가

질문: 통과한 조합 각각이 얼마나 좋은가.

- **B-1 강의 단위 가치 v(c) (per-course)** — 해시 탐색, 이진 탐색
  `중요도 × 학점 + 시간대 + 건물 + 카테고리 + 이수요건 + 교수 페널티` 합산. 교수 항이 같은 그룹 분반들 사이의 결정적 신호.
- **B-2 전이 비용 전계산 (per-pair)** — 플로이드-워셜, (다익스트라)
  건물 간 최단 이동 시간 표 산출. 한 번 계산하면 이후 O(1) 룩업. 시간표 이동 합산은 인접 슬롯의 **슬롯별 건물**로 룩업한다.
- **B-3 누적 점수 최적화 + top-K 추출 (per-schedule)** — 0-1 배낭(상한 가지치기) + 백트래킹  
  ※ 실제 구현: `valuation._enumerate_feasible_subsets`의 백트래킹이 `knapsack_01` 상한으로 가지치기. 명세상 거론됐던 행렬 경로 DP는 **미채택**(`matrix_path_dp.py`는 현재 import되지 않는 dead code).
  시간 슬롯 격자 DP로 정확해 산출, **그룹당 최대 1개 분반 선택 제약 적용**, `must_include_groups`는 그룹 내 점수 최대 분반 강제 포함, 시간표 단위 후처리 페널티 적용, 백트래킹으로 top-K 복원.

**점수 식** (B-1):
```
v(c) = 중요도(c) × 학점(c)
     + 시간대 페널티(c)
     + 건물 페널티(c)            ← 강의가 쓰는 distinct 건물 가중치 합 (슬롯 단위)
     + 카테고리 가중치(c)
     + 이수요건 가중치(c.requirement)
     + 교수 가중치(c.professor)         ← 신규 (분반 선호 표현)
```

### 9.4 C — 선택과 비교

질문: 무엇을 어떻게 골라 사용자에게 보여줄 것인가.

- **C-1 상위 N개 정렬·동률 처리 (per-set)** — 합병 정렬(안정)
  점수 내림차순 + 동률 안정, 다양성 후처리.
- **C-2 후보 쌍 비교 골격 (per-pair)** — LCS, (편집 거리)
  공통 백본 + 차이 강의 추출.
- **C-3 강의별 포함·배제 사유 색인 (per-course)** — 해시 탐색
  설명 가능성 §4-2 자료 (제외 사유 1순위). **그룹 관련 사유 코드 3개 추가**: `A-1.group_excluded`, `A-2.group_duplicate`, `B-3.group_loser`.

### 9.5 알고리즘 매핑 (algorithms.md 횡단)

| 카테고리 | 알고리즘 | 위치 |
| -------- | -------- | ---- |
| 정렬 | 시간 정렬 | A-2 |
| 정렬 | 합병 정렬 | C-1 |
| 탐색 | 이진 탐색 | A-2, B-1 |
| 탐색 | 해시 탐색 | A-1, B-1, C-3 |
| 탐욕 | 활동 선택 | A-3 |
| 탐욕 | 다익스트라 (옵션) | B-2 |
| DP | 플로이드-워셜 | B-2 |
| DP / 백트래킹 | 0-1 배낭(상한 가지치기) + 백트래킹 | B-3 |
| DP | LCS | C-2 |
| DP | 편집 거리 (옵션) | C-2 |
| 기타 | 위상 정렬 (옵션) | A-3 |

5개 카테고리 모두 사용. 필수 9개 + 옵션 3개.

### 9.6 노드 간 계약 (잠정 — 필드명·구조 변경 가능성 높음)

```
A → B:  FeasibilityResult
  { candidates, must_include_mask, compatible[][], travel_time_table[][],
    ordered_by_start, credit_ceiling_reachable, infeasibility_reason }

B → C:  ValuationResult
  { top_k_candidates: [{ courses, used_credit, total_score, score_breakdown }],
    num_total_feasible, best_score, k_threshold_score }

C → 응답:  SelectionResult
  { ranked_schedules, pairwise_diff, course_rationale,
    diversity_adjustment_applied }
```

⚠️ 본 계약은 반영률 60% 중에서도 변동성이 가장 큰 부분. `app/schemas/` 이동 시 재설계됨.

### 9.7 시간 복잡도 요약

```
T = O( V³ + N² + N·C + Ñ²·L² )
```

지배항 — V³ (플로이드-워셜) 또는 N² (충돌 행렬).
현실 입력 (N=30, V=20, C=21, Ñ=5, L=6): 약 11,000 연산 ≈ 1 ms.
응답 시간 지배항은 알고리즘이 아니라 LLM 호출 (~1초).

### 9.8 Infeasibility 조기 종료

A-3가 `credit_ceiling_reachable=false` 또는 필수 강의 충돌 검출 시 B·C 실행 안 함.
트리 출력은 `InfeasibilityReport` (어느 제약을 풀면 가능해지는지 진단 포함).
트리의 *조기 종료 경로*로 base 계약에 명시 필요.

### 9.9 확정·변동 항목 분리표

확정 시점(2026-05-17)에 무엇이 잠겼고 무엇이 구현 시점까지 열려 있는지의 권위 있는 표.

| 부분 | 상태 | 비고 |
| ---- | ---- | ---- |
| A/B/C 책임 기반 3분할 | ✓ 확정 | 의존성 구조에 따른 자연 분해 |
| A-1·A-2·A-3 자식 분할 | ✓ 확정 | per-course / per-pair / per-subset 단조 증가 |
| B-1·B-2·B-3 자식 분할 | ✓ 확정 | per-course / per-pair / per-schedule |
| C-1·C-2·C-3 자식 분할 | ✓ 확정 | per-set / per-pair / per-course (역방향) |
| 핵심 알고리즘 자리 (필수 9개) | ✓ 확정 | 해시·정렬·이진 탐색·활동 선택·플로이드-워셜·**백트래킹**·0-1 배낭·합병 정렬·LCS (행렬경로 DP는 미채택) |
| 시간 복잡도 점근식 | ✓ 확정 | `T = O(V³ + N² + N·C + Ñ²·L²)` |
| B-2 플로이드-워셜 위치 | ✓ 확정 | 계산은 A 단계에서 일어나고 B는 룩업 (계약 (가)) |
| LLM-A upstream(자유 텍스트 → 수치화) | ✓ 결정 | `product.md` §5.2 보류 — 단순화 우선, 추후 가치 명확 시 도입 |
| 옵션 알고리즘 (다익스트라·위상 정렬·편집 거리) | ◐ 구현 시 결정 | 자리는 박혀 있으나 채택 여부는 `app/libs/` 구현 시점 |
