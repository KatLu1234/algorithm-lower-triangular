## 1. 한 줄 요약

고려대 학생이 강의 후보를 입력하면 이동 시간·학점·중요도를 고려한 최적 시간표를 받고, **어떻게 그 결과가 나왔는지를 알고리즘 단위로 확인·이해할 수 있도록** 해주는 학습 겸용 도구.

> "(누구) 고려대 학생이 / (상황) 매 학기 시간표를 짤 때 / (가치) 빠르고 정확하면서도 결과의 근거를 이해할 수 있도록 / (방식) 알고리즘 기반 최적화 + LLM 단계별 설명으로 / (형태) 학습 겸용 도구를 제공한다."

---

## 2. 목적성 (Why)

### 2.1 풀려는 문제

고려대 학생은 매 학기 강의 후보 중 (i) 시간이 겹치지 않고 (ii) 학점 한도를 넘지 않고 (iii) 본인이 더 듣고 싶은 과목이 우선되며 (iv) 캠퍼스 내 이동 시간이 현실적인 — 이 네 가지 제약을 동시에 만족하는 조합을 손으로 엑셀에서 만들고 있다. 제약이 4개 이상이라 사람이 손으로 푸는 데 한계가 있고, 빠뜨린 제약을 뒤늦게 발견해 재작성하는 일이 잦다.

### 2.2 이 제품이 존재해야 하는 이유

기존 학교 포털은 시간 충돌만 검사할 뿐 이동 시간·중요도·학점 합을 동시에 최적화하지 않는다. 일반 시간표 앱은 학교 건물 거리 데이터가 없다. **직접 짜는 것보다 빠르고, 빠진 제약 없이 보장된 결과를 주며, "왜 이 시간표가 나왔는지"를 알고리즘 단위로 설명해 학습에도 쓸 수 있는** 도구는 없다.

부가적으로 본 도구는 algorithms.md의 핵심 알고리즘 5개 카테고리(정렬·탐색·탐욕·DP·기타)를 *필요해서* 사용하는 자연스러운 형태로 시연한다.

### 2.3 비-목적 (Non-goals)

- 수강신청 자동화(포털 자동 신청)는 하지 않는다.
- 성적·GPA 예측은 하지 않는다.
- 교수·강의 평가 데이터로 추천하지 않는다.
- 학기 외 장기 커리큘럼 추천은 하지 않는다 (단일 학기에 한정).
- 고려대 외 학교 데이터는 본 과제 범위에서 우선 다루지 않는다.
- 모바일 우선 UX는 하지 않는다 (PC 브라우저 우선).
- 친구 시간표 매칭·동시 수강 추천은 하지 않는다 (외부 인원 데이터 의존).

## 3. 기대 효과 (What changes)

### 3.1 정성적 효과

학생이 엑셀로 시간표를 짜는 행위 자체가 사라지고, **후보 강의 입력 → 시간표 N개 검토 → 결정**으로 흐름이 단축된다. "왜 이 시간표인가"를 사용자가 이해한 상태로 결정하므로 학기 중 후회·재조정이 줄어든다. 사용자는 알고리즘 분해 트리를 통해 *각 단계에서 왜 그 알고리즘이 쓰였는가*를 학습한다.

### 3.2 정량적 지표

| 지표 | 목표 값 | 측정 방법 |
| ---- | ------- | --------- |
| 알고리즘 산출 시간 (LLM 제외) | ≤ 50 ms (강의 후보 ≤ 50개, 건물 ≤ 30개) | 단위 테스트 |
| 사용자 응답 전체 시간 (LLM 포함) | ≤ 3 초 | 서버 로그 |
| 제약 위반 응답 | 0 건 | 통합 테스트 |
| 응답에 등장하는 알고리즘 카테고리 수 | ≥ 4 (algorithms.md 5개 중) | LLM 응답 검증 |
| 상위 N개 후보 다양성 (백본 일치율) | ≤ 80% | C-1 다양성 후처리 측정 |

## 4. 우선순위 (Trade-off 발생 시 무엇이 먼저인가)

```
1. (최우선) 정확성              — 제약 위반(시간 충돌·학점·이동·고정/제외) 0건
2.          설명 가능성        — 왜 이 시간표인가가 알고리즘 단위로 추적 가능
3.          유저 중요도 반영 충실도 — 사용자가 매긴 중요도가 결과에 그대로 반영
4.          모순·불가능 입력 안내 — 불가능 시 "어느 제약을 풀면 가능한지" 진단
5.          검증 가능성        — 사람이 손으로 검산 가능한 응답 구조
6.          응답 속도          — 알고리즘 ≤ 50 ms, 전체 ≤ 3 초
7.          결과 다양성        — 상위 N개가 의미 있게 다름
8.          이동 부담 최소화    — 동률 시 타이브레이커
9.          사용자 제어권      — (본 과제 범위에서 후순위)
10. (가장 낮음) 결과 안정성    — (본 과제 범위에서 가장 후순위)
(이후 — 작업 시간 예산이 남으면) UI 다듬기 → 코드 구조화
```

### 4.1 우선순위 근거

- **1~3**은 한 줄 요약(균형 모델)의 정의 그 자체 — 정확성, 알고리즘 설명, 사용자 의도 존중.
- **4~5**는 결과를 사용자가 받아들이는 신뢰 기반 — 불가능을 설명하고, 결과를 검증 가능하게.
- **6**은 사용자 인내 한도의 하한선 — 더 내릴 수 없음.
- **7~8**은 결과 품질 보조.
- **9~10**은 본 과제 범위(한 학기 시연 + 실용 데모)에서 후순위. 향후 인터랙티브 편집 UI를 도입할 때 위로 올라옴.

### 4.2 예외

다음 충돌 케이스에서는 표준 우선순위를 다음과 같이 적용한다.

- **정확성 vs 응답 속도**: 정확한 결과가 3초 안에 안 나오는 입력 규모일 때, 정확성을 깎지 않고 **"계산 시간 초과"를 정직하게 보고**한다. 가짜 응답 위조 금지 (`base/CLAUDE.md` §3.5).
- **중요도 충실도 vs 이동 부담**: 중요도 5점 강의가 멀어 다른 강의 두 개와 양립 불가일 때, **중요도 충실도 우선** (5점 강의 포함, 다른 두 개 중 하나 양보).
- **다양성 vs 점수 최대화**: 상위 N개가 거의 동일한 백본일 때, **점수 5% 양보 한도까지 다양성 페널티 적용**. 그 이상 휴리스틱 적용 금지.
- **사용자 제어권 vs 결과 안정성**: 본 과제 범위에서는 인터랙티브 편집을 비-목적으로 두므로 이 충돌은 자연 해소.

### 4.3 세부 우선순위 (상위 3개 항목의 내부 구조)

§4 우선순위 표의 1·2·3위는 그 안에 다시 세부 구조가 있다.

#### 4.3.1 정확성 내부

**전제 (모두 충족 필수, 우선순위 대상 아님)**
- 데이터 정합성: 입력 강의 시간이 well-formed, 건물 코드 존재, 학점·중요도 범위 검증. 위반 시 **결과를 내지 말고 입력 단계에서 거절**.

**핵심 hard 제약 (모두 0 위반 필수, 위반 시 사용자 신뢰 손상 큰 순서)**
1. 사용자 명시 제약 (고정·제외 강의) 준수 — 가장 치명적
2. 시간 충돌 0건
3. 이동 시간 가능성 (강의 i 종료 + 이동 시간 ≤ 강의 j 시작)
4. 학점 한도 (상한, 명시되었다면 하한도)
5. 강의 중복 없음 (같은 과목 코드 두 번)

**파생**
- 산술 정확성: 보고된 점수 합·학점 합·이동 시간 합이 실제 시간표와 일치.

#### 4.3.2 설명 가능성 내부 (응답에 우선 배치할 순서)

1. **제외 사유 (왜 안 들어갔는가)** — 사용자가 가장 의심하는 자리. 1순위.
2. **포함 사유 (왜 들어갔는가)** — 결정 흐름의 흔적.
3. **단계별 알고리즘 narration** — "1단계 정렬 → 2단계 활동 선택 → 3단계 배낭 → ..." 형태.
4. **알고리즘 선택 근거** — "여기서 왜 0-1 배낭인가."
5. **대안 비교 (1등 ↔ N등 차이)** — 상위 N개의 가치를 살리는 자리.
6. **민감도 정보** — "이 강의 빼면 점수 -5" 형식. 부가 가치, 후순위.

#### 4.3.3 유저 중요도 반영 충실도 내부

1. **명시 제약 절대 준수** (고정·제외 락) — §4.3.1의 1번과 같은 검사 대상.
2. **시스템 자체 판단 금지** (암묵적 가중치 0) — 시스템이 사용자 입력 외 가중치를 임의로 끼워 넣지 않음.
3. **단조성** — 5점 ≥ 4점이 항상 우대받음 (hard 제약 위반 제외).
4. **충돌 시 사용자 의도 보존** — 두 5점 강의가 충돌하면 시스템이 임의로 하나를 고르지 않고, 두 결과로 분리하거나 사용자에게 물음.
5. **점수 비례 반영** — 1~5점 차이가 결과에서 의미 있는 차이를 만들어야 함.
6. **가중치 변경에 비례 반응** — 사용자가 중요도를 바꾸면 결과도 그 방향으로 변화. ⚠️ §4의 10번 "결과 안정성"과 직접 충돌, 본 우선순위가 위.

### 4.4 LLM 역할 분담 (시스템 불변항)

> **시간표 결정은 항상 알고리즘이 한다.** LLM은 다음 두 자리에만 관여한다.
>
> (a) **입력 자유 텍스트의 수치화** (선택 기능 — 도입 여부는 §5.2 참고)
> (b) **결과의 자연어 설명**
>
> LLM이 산출한 어떤 값도 **알고리즘 검증 없이는 결과에 반영되지 않는다.** 사용자가 명시한 제약(고정·제외 강의, 1~5 중요도, 학점 한도, blackout 시간대)은 시스템이 임의로 무시하지 않는다.

이 약속이 깨지면 §4의 1·2·3위가 동시에 손상된다.

## 5. 범위 (Scope)

### 5.1 포함되는 기능

**입력**
- 강의 후보 입력: 강의명·시간·학점·건물·카테고리(전공/교양/일선)
- 학점 한도 입력 (상한, 선택적으로 하한)
- 필수 포함·절대 제외 강의 표시
- Blackout 시간대 입력 (외부 일정·통학 등)
- 강의별 중요도 1~5점 입력

**처리** (`drafts/algorithm-tree.md` §9 참조, 반영률 60%)
- A 가능성 분석 — 강의 풀 정제, 시간 충돌 행렬, 후보 공간 가지치기
- B 가치 평가 — 강의 단위 가치 산출, 이동 시간 전계산(플로이드-워셜), 누적 점수 DP(행렬 경로 + 0-1 배낭)
- C 선택과 비교 — 상위 N개 정렬, 후보 간 LCS 비교, 강의별 사유 색인

**출력**
- 상위 N개 최적 시간표 (N = 3~5)
- 각 시간표의 점수 분해 (중요도 기여·시간대 페널티·이동시간·압축 등)
- 후보 간 비교 (공통 백본, 차이 강의)
- 각 강의의 포함/배제 사유 색인
- 알고리즘 단계별 설명 (LLM 생성)
- 불가능 입력 시 "어느 제약을 풀면 가능한지" 진단

### 5.2 보류 / 차후 검토

- **자유 텍스트 메모 → LLM 수치화 (단계적 도입)**: 입력 단순화 권장 입장이 있으나(structured 1~5 점수·체크박스로 충분), 가치가 명확하면 추후 도입. 도입 시 §4.4 (b)에 (a)를 추가하고 LLM 응답을 사용자가 확인하는 단계 필수.
- 사용자 제어권 (강의 고정·제외·가중치 재조정 후 재계산): §4의 9번. 본 과제 다음 단계.
- 결과 안정성 후처리 (입력 변동에 대한 비례 반응): §4의 10번. 본 과제 다음 단계.
- 강의 평가·교수 평점 데이터 활용: §2.3 비-목적.
- 친구 시간표 매칭: §2.3 비-목적.
- 다음 학기 커리큘럼 추천: §2.3 비-목적.
