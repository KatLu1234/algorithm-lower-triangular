# CLAUDE.md — base 레벨 작업 지침

이 문서는 `frontend`, `server`, `llm-include` **세 영역의 경계에 영향을 주는 변경**을 Claude가 작업할 때 따라야 할 절차를 정의합니다.
개별 영역 내부의 세부 규칙은 각 폴더의 문서를 따르고, 본 지침은 **계층 사이 변경**에 한정해 적용됩니다.

먼저 짝꿍 문서를 반드시 읽으세요. 작업 종류에 따라 우선순위가 다릅니다.

| 문서 | 무엇을 정의하는가 | 언제 읽는가 |
| ---- | ----------------- | ----------- |
| [`./product.md`](./product.md) | 제품의 **목적성·기대 효과·우선순위**. 트레이드오프가 생겼을 때의 결정 순서(예: `성능 > 구조화`). | 모든 base 변경 전. 특히 두 가치가 충돌할 때(속도 vs 정확성, 기능 추가 vs 단순성 등). |
| [`./user-experience.md`](./user-experience.md) | **유저가 기대할 수 있는 경험** — 페르소나·핵심 여정·인터랙션 원칙·접근성·UX 비-목표. | 화면 변경, 에러 문구·로딩 처리, 응답 메시지 톤, 새 기능의 사용자 노출 방식을 결정할 때. |
| [`./architecture.md`](./architecture.md) | `frontend ↔ server ↔ llm-include` **계층 조합 설계**, **기술 스택**, 인터페이스 규약. | 계층 경계(스키마·LLM 흐름·새 엔드포인트 계약), 또는 **기술 스택 추가/교체/제거** 시. |
| [`./progress.md`](./progress.md) | base 문서들의 **변경 이력**과 현재 베이스라인 스냅샷. | base 문서를 편집할 때마다(매번). 결정이 언제·왜 굳어졌는지 확인할 때. |
| [`./tasks.md`](./tasks.md) | **전체 작업 칸반 인덱스** + 영역 진행 요약 + 교차 영역 카드. | 팀원이 자기 작업·전체 진행을 확인할 때. 영역별 상세 카드는 `<영역>/tasks.md`. |

세 문서의 관계:
- `product.md`는 **"왜·무엇을·무엇부터"** 를 정한다 → 충돌 시 최종 기준.
- `user-experience.md`는 **"사용자에게 어떻게 보이고 느껴지는가"** 를 정한다 → 화면·메시지·인터랙션 기준.
- `architecture.md`는 **"내부에서 어떻게 조립되는가"** 를 정한다 → 코드 배치·의존 방향 기준.

판단이 어긋날 때의 우선순위: **`product.md` > `user-experience.md` > `architecture.md`**.
즉 제품 목적·우선순위가 UX 관성이나 기존 아키텍처보다 위에 있다(단, 아키텍처를 바꾼다면 별도 승인 절차 — 본 문서 §1, §2).

## 1. 작업을 base 변경으로 분류하는 기준

다음 중 하나라도 해당되면 **base 변경**이다. base 변경을 시작하기 전, 사용자에게 변경 요약과 영향 범위를 먼저 보고하고 승인을 받는다.

- 새 HTTP 엔드포인트가 **frontend에서 호출되는 새 계약**을 만든다.
- 응답·요청 스키마(`app/schemas/*`)의 필드를 추가/삭제/이름 변경한다.
- LLM 호출 흐름이 새로 생기거나, 기존 흐름의 입출력 구조가 바뀐다.
- `claude/llm-include/` 디렉터리 구조나 파일 명명 규칙이 바뀐다.
- `app/libs/llm_context.py`, `app/libs/llm_client.py`, `app/core/config.py`의 공개 인터페이스가 바뀐다.
- 새 외부 의존(LLM 공급자, 벡터 DB, 캐시 등)을 도입한다.
- [`product.md`](./product.md)의 **우선순위·목적성·기대 효과**가 바뀐다.
- [`user-experience.md`](./user-experience.md)의 **약속·여정·UX 비-목표**가 바뀐다.

반대로 다음은 base 변경이 **아니다** — 해당 영역의 지침만 따라 진행한다.

- 한 라우트 함수의 내부 로직 수정 (계약 변경 없음).
- 알고리즘 본체(`app/libs/lower_triangular.py`) 구현 개선.
- 프롬프트 문구 *표현* 다듬기 (메시지 구조·필드는 동일).
- 프론트엔드 화면 스타일링.

## 2. 작업 전 — 체크리스트

1. `claude/CLAUDE.md`(최상위) → `claude/base/architecture.md` → 이 문서 순서로 읽었는지 확인.
2. 변경하려는 항목을 architecture.md의 **§2 기술 스택**·**§5 인터페이스 규약**·**§6 디렉터리**와 비교해 어긋나지 않는지 확인.
3. 다음을 한 단락으로 사용자에게 제시하고 승인 받는다.
   - **무엇을** 바꾸려는가
   - **어느 계층 경계가** 영향받는가 (frontend / server / llm-include 중 어디)
   - **마이그레이션이 필요한 파일**(스키마 변경 시 frontend 호출부 등) 목록
   - **롤백 방법**(이전 스키마 유지 vs 신규 필드 옵셔널 등)

## 3. 작업 중 — 규칙

### 3.1 의존성 방향 유지
- `frontend → server → llm-include` 방향을 거스르는 import·호출을 만들지 않는다.
- `llm-include/` 내부에서 `app/`의 코드를 참조하는 형태(템플릿 안에 import 문 등)는 금지.
- `app/api/endpoints/*.py`가 `claude/llm-include/`를 **직접 읽지 않는다**. 반드시 `app/libs/llm_context.py`를 경유한다.

### 3.2 스키마 변경의 안전 순서
필드 추가·변경은 다음 순서로 한다(왼쪽 → 오른쪽이 동작 가능 상태를 유지).

1. `app/schemas/`에 새 필드를 **옵셔널**로 먼저 추가.
2. 서버 라우트가 새 필드를 채워 응답하도록 수정.
3. frontend가 새 필드를 사용하도록 수정.
4. (충분히 안정된 뒤) 옛 필드를 제거하거나 필수화.

요청 스키마의 필수 필드를 즉시 추가하면 frontend가 깨진다. 반드시 옵셔널 → 필수 2단계로 진행한다.

### 3.3 LLM 호출 추가 시 절차
1. `claude/llm-include/prompts/<task>.md` 파일을 만든다. 상단 메타 헤더 포함.
2. 필요하면 `claude/llm-include/examples/<task>/case-*.json`에 few-shot 케이스를 추가한다.
3. `app/libs/llm_context.py`에 `build_<task>(payload) -> messages` 함수를 추가한다 — 파일을 읽고 합치는 역할만 한다.
4. `app/libs/llm_client.py`는 손대지 않는다(공통 호출자). 호출은 라우트에서 `llm_client.complete(build_<task>(payload))` 패턴.
5. 라우트와 응답 스키마는 `server/` 지침에 따라 추가한다.

### 3.4 시크릿 / 설정
- `.env` 값은 코드·문서·로그·예시 어디에도 노출하지 않는다.
- 새 환경변수가 필요하면 `app/core/config.py`에 정의하고, `.env.example`(없으면 신규 생성)에 **이름과 더미 값**만 추가한다.

### 3.5 가짜 데이터 / 더미 사용 금지
- LLM 호출이 막혀 있더라도 응답을 **하드코딩으로 위조**하지 않는다. 막혔으면 막혔다고 보고하고 진행 여부를 묻는다.
- 테스트 목적의 더미 응답은 `tests/` 폴더 안에서만 사용.

## 4. 작업 후 — 보고 양식

마지막 응답에 아래 5가지를 모두 포함한다.

1. **변경 파일 목록** (계층 표시: `[F]/[S]/[I]/[B]` = frontend/server/llm-include/base).
2. **계약 영향**: 어떤 엔드포인트·스키마·프롬프트가 새/변경/삭제되었는지 한 줄씩.
3. **검증 결과**: 최소 1개 케이스의 입출력 확인. 통과·실패 모두 기록.
4. **사용자 후속 작업 체크리스트**: `.env` 키 추가, frontend 빌드, 마이그레이션 등.
5. **progress 갱신 상태**: 어느 `progress.md`가 갱신됐는지(또는 "해당 없음" 사유) 명시. §5 규칙 참고.

## 5. 진행 이력 (`progress.md`) 갱신 규칙

각 영역마다 `progress.md` 파일이 있고, 갱신 시점이 영역별로 **다릅니다**. 반드시 구분해서 적용한다.

### 5.1 `claude/base/progress.md` — **매번** 갱신
- `claude/base/` 안의 **어떤 문서가 바뀌든** 같은 응답 안에서 `base/progress.md`의 §2 변경 이력 표에 한 줄을 추가한다.
- 오타·외형 수정도 포함한다(유형 컬럼에 "정정" 또는 "외형"으로 표기).
- 새 파일이 추가/제거되면 §1 스냅샷 표도 함께 갱신한다.
- **예외 없음**: base 문서 편집과 `progress.md` 미갱신이 동시에 일어나면 보고서에 누락으로 표기되어야 한다.

### 5.2 `claude/server/progress.md`, `claude/frontend/progress.md`, `claude/llm-include/progress.md` — **조건부** 갱신
다음 **두 경우에만** 갱신한다.
1. **사용 기술 변경** — 프레임워크·라이브러리·DB·LLM 공급자·템플릿 엔진 등의 도입/교체/제거.
2. **별도 지침 추가** — `claude/base/` 일반 규칙으로 안 풀려서, 해당 영역에만 적용되는 결정이 새로 굳어질 때.

다음은 **기록하지 않는다**(git 커밋으로 충분).
- 라우트 추가, 컴포넌트 추가, 알고리즘 구현, 스타일 손질, 프롬프트 문구 다듬기, 버그 수정, 일반적 리팩터링.

### 5.3 갱신 절차
1. 변경한 문서/항목과 같은 응답에서 해당 `progress.md`를 함께 편집한다.
2. §2 변경 이력 표에 한 줄 추가: 날짜·파일/항목·변경 유형·요약·사유.
3. 스냅샷 표(§1)에 영향이 있으면 그 표도 갱신.
4. 작업 후 보고(§4)에 "progress 갱신함: `base/progress.md`" 처럼 명시한다.

### 5.4 판단이 애매할 때
- "이게 기술 변경인지, 일반 코드 변경인지" 헷갈리면 → 기록한다(보수적으로).
- "이게 별도 지침인지, 본문 한 줄짜리 메모인지" 헷갈리면 → 사용자에게 묻는다.

## 6. `product.md` · `user-experience.md` 활용 규칙

이 두 문서는 Claude가 코드를 짤 때의 **판단 기준**입니다. 단순 참고 자료가 아닙니다.

### 6.1 작업 전
- 본 문서 §1의 분류표를 보고 어느 문서를 더 비중 있게 봐야 하는지 정한다.
- 두 문서 중 관련 섹션이 **비어 있으면** 코드를 먼저 짜지 말고 사용자에게 채워달라고 요청한다. 빈 칸을 임의 추론으로 메우지 않는다.

### 6.2 의사결정 중
- 트레이드오프가 보이면 곧장 [`product.md`](./product.md) §4 우선순위를 인용한다. 예:
  > "정확성이 응답속도보다 위(`product.md` §4)이므로 캐싱 대신 정확한 재계산을 택했다."
- UI 문구·에러 메시지·로딩 표시는 [`user-experience.md`](./user-experience.md) §4 인터랙션 원칙을 그대로 따른다. 본인 취향으로 톤을 바꾸지 않는다.
- 두 문서가 **서로 충돌**하는 것처럼 보이면 §1의 우선순위(`product.md > user-experience.md > architecture.md`)에 따라 결정하고, 충돌 사실을 보고에 명시한다.

### 6.3 문서 갱신
- 이 두 파일은 **사용자 승인 없이 본문을 수정하지 않는다**. (오타·줄바꿈 같은 외형 수정은 예외이나, base 영역이므로 `progress.md`에는 외형 변경도 기록한다.)
- 사용자가 직접 채우거나 수정한 뒤에는, 변경된 항목이 기존 코드와 어긋나지 않는지 Claude가 **재검토 보고**를 제공한다.
- 새 항목이 추가되면 §8 빠른 참조와 본 문서 §1의 분류표 링크가 여전히 유효한지 확인한다.

### 6.4 인용 양식
보고 시 결정 근거를 적을 때 다음 형식을 사용한다.

```
근거: product.md §4 — "정확성 > 응답속도"
근거: user-experience.md §3.2 — "약속 2: 5초 이내 결과 미리보기"
```

이렇게 출처를 박아두면 나중에 결정이 바뀐 이유를 추적할 수 있다.

## 7. 절대 금지 사항

- frontend에서 LLM API 키 사용 또는 외부 LLM 직접 호출.
- `endpoints/` 안에서 프롬프트 문자열 하드코딩.
- `llm-include/`에 `.py` 추가.
- 계층 화살표를 거스르는 import (예: `app/libs/llm_context.py`가 `app/api/...`를 import).
- 이 문서나 `architecture.md`, `product.md`, `user-experience.md`를 **사용자 승인 없이** 임의 수정 (오타 수정은 예외).
- `product.md` / `user-experience.md`의 빈 섹션을 **추측으로 채워** 그 추측을 근거로 코드 결정을 내리기.
- 큰 폴더 이름·구조 변경(`claude/`, `app/`)을 본인 판단으로 진행.
- base 문서를 편집하면서 `base/progress.md`를 함께 갱신하지 않기 (§5.1).
- 일반 코드 변경을 `server/`, `frontend/`, `llm-include/`의 `progress.md`에 잘못 기록하기 (§5.2).
