# pages/index.md — 프론트엔드 페이지 구조 인덱스

> **이 폴더의 역할**
> 사용자가 보는 화면(페이지) 단위 설계 문서를 **한 페이지당 한 파일**로 모은 곳.
> 라우팅·인증 흐름·페이지 간 전이는 본 문서에서, 페이지 내부 UI/상태/API는 각 파일에서.
>
> **상태: 설계안.** 실제 구현은 `frontend/src/` 코드를 손대는 별도 단계
> (`../../CLAUDE.md` §4.2 — 큰 리팩터링은 사용자 승인 후).

## 1. 페이지 목록 (4개)

| URL | 페이지 | 문서 | 인증 필요 |
| --- | --- | --- | --- |
| `/login` | 로그인 / 회원가입 | [login.md](./login.md) | 아니오 (비인증 전용) |
| `/` | 메인 (허브) | [main.md](./main.md) | 예 |
| `/timetable` | 시간표 짜기 | [timetable.md](./timetable.md) | 예 |
| `/courses` | 강의 검색 | [course-search.md](./course-search.md) | 예 |

페이지가 늘어나면 본 표와 §2 다이어그램만 갱신하고, 페이지 본문은 새 파일을 추가한다.

## 2. 라우팅 다이어그램 — 사용자 여정

```
                       (앱 진입)
                          │
            ┌─────────────┴─────────────┐
       토큰 없음                     토큰 있음 (만료/위변조 가능)
            │                            │
            ▼                            ▼
        ┌────────┐                  ┌──────────┐
        │ /login │                  │  /me 검증 │
        └────┬───┘                  └────┬─────┘
   로그인/가입 성공                   성공 │ │ 실패
            │                            │ ▼
            ▼                            │ /login
        ┌──────┐  ◀──────────────────────┘
        │  /   │ 메인 (허브)
        └──┬─┬─┘
           │ │
   "시간표 짜기" │ "강의 검색"
           │ │
           ▼ ▼
   ┌──────────────┐    ┌──────────────────┐
   │  /timetable  │    │    /courses      │
   │  시간표 짜기   │ ◀─▶│   강의 검색       │
   └──────────────┘    └──────────────────┘
           ▲                    │
           │  "내 풀로 추가"      │
           └────────────────────┘
```

핵심 흐름:
- 비인증 사용자는 어떤 보호 라우트에 접근해도 `/login`으로 리다이렉트(원래 가려던 URL은 `from` state로 보관 → 로그인 성공 후 그곳으로 복귀).
- 메인은 작업 시작점이며 두 기능 페이지로 가는 진입 카드만 둔다(많은 일을 시키지 않음).
- 강의 검색 → 시간표 짜기로 후보 풀이 흘러간다(반대 방향은 강의 검색에서 "내 풀에 이미 담김" 표시로만 반영).

## 3. 라우터 · 가드 구현 패턴

라우터는 `react-router-dom`(v6+). 단일 진입 `<BrowserRouter>`에 4개의 `<Route>`를 등록하고, 메인·시간표·강의 검색은 `<ProtectedRoute>`로 감싼다.

```tsx
// 의사 코드 — 실제 파일/경로는 구현 시 결정
<BrowserRouter>
  <Routes>
    <Route path="/login" element={<LoginPage />} />
    <Route element={<ProtectedRoute />}>
      <Route path="/" element={<MainPage />} />
      <Route path="/timetable" element={<TimetablePage />} />
      <Route path="/courses" element={<CourseSearchPage />} />
    </Route>
    <Route path="*" element={<Navigate to="/" replace />} />
  </Routes>
</BrowserRouter>
```

`<ProtectedRoute>`의 책임:
1. 마운트 시 `getToken()` 으로 로컬 토큰을 본다. 없으면 즉시 `<Navigate to="/login" state={{ from }} />`.
2. 있으면 `fetchMe()`(`GET /auth/me`)로 1회 검증. 실패면 `/login`으로.
3. 검증 동안에는 전체 화면 `LoadingState`(현재 `App.tsx`의 "세션을 확인하는 중…" 패턴 유지).

`<LoginPage>` 안에서는 인증된 사용자가 들어오면 `from` 또는 `/`로 즉시 리다이렉트해, 로그인 화면을 재방문하지 못하도록 한다.

## 4. 페이지 간 이동 흐름 (전이 표)

| 출발 → 도착 | 트리거 | 데이터/상태 전달 |
| --- | --- | --- |
| `/login` → `from` 또는 `/` | 로그인/가입 성공 | 토큰 localStorage 저장, `setCurrentUser`. |
| `/` → `/timetable` | "시간표 짜기" 카드 클릭 | (전역 상태의) 내 풀이 시간표 페이지에서 보임 |
| `/` → `/courses` | "강의 검색" 카드 클릭 | 검색 페이지의 캐시된 카탈로그(있으면) 그대로 사용 |
| `/courses` → `/timetable` | "내 풀에 담기" 후 "시간표 짜러 가기" | 내 풀 갱신 → 시간표 페이지가 풀 기반으로 폼 초기화 |
| 어디서든 → `/login` | 로그아웃 또는 토큰 만료 | 토큰 제거, 사용자 상태 초기화 |

> **"내 풀"의 위치**: 데모 단계에서는 React 전역 상태(Context) + localStorage 캐시.
> 영속화는 차후 `preference_courses` 테이블로(서버 DB 설계 Phase 2 — `claude/server/db/preference_courses.md`).
> 본 문서에서는 *프론트 상에서의 위치*만 정의하고, 영속 정책은 서버 영역으로 위임.

## 5. 공통 셸 (Layout) · 헤더 · 푸터

- 인증 후 페이지(`/`, `/timetable`, `/courses`)는 같은 셸을 공유한다 — 상단에 로고/타이틀, 우상단에 사용자 표시 + 로그아웃 + (선택) 다른 페이지 단축 링크. 셸은 `<ProtectedRoute>` 의 `<Outlet>` 자식들을 감싼다.
- 로그인 페이지는 셸 없이 단독 풀스크린(현재 `Login.tsx` 패턴 유지).
- 색·간격은 `frontend/docs/demo-layout.md` §1.1 색상 토큰을 따른다(브랜드 마룬 + 크림). 이 결정은 본 다중 페이지 구조에서도 그대로 승계.

## 6. demo-layout.md와의 관계

`frontend/docs/demo-layout.md` 는 **단일 페이지·3분할(좌 사이드바 + 중앙 시간표/채팅 + 우 후보 리스트)** 데모를 정의한 문서다. 본 다중 페이지 구조는 그 단일 페이지를 분해해 다음과 같이 흡수한다:

| demo-layout.md 영역 | 본 구조의 위치 |
| --- | --- |
| 좌 사이드바 · 계정 | 공통 헤더의 사용자 표시 + 로그아웃 |
| 좌 사이드바 · 저장한 과목 | `/courses` 결과 + "내 풀" + `/timetable` 폼 초기 |
| 중앙 · 선택된 시간표 | `/timetable` 결과 영역 (`TimetableGrid` 재사용) |
| 중앙 · 채팅 | `/timetable` 내 `NaturalLanguageInput` (LLM-A) |
| 우 · 후보 리스트 | `/timetable` 결과의 `ranked_schedules` 렌더링 |

3분할 한 화면 데모가 "데모 시연용 한 페이지"라면, 본 구조는 **운영형 다중 페이지**다. 둘은 공존하지 않으며, 다중 페이지 구조 채택 후 demo-layout.md는 *디자인 영감 자료*로만 참고한다(컴포넌트·색 토큰·격자 디자인은 재사용).

## 7. 페이지 추가 절차

새 페이지를 추가할 때는:

1. 본 문서 §1 표·§2 다이어그램·§4 전이 표에 한 행씩 추가.
2. `pages/<slug>.md` 파일을 만들어 [공통 항목](#8-페이지-md-공통-항목)을 채운다.
3. `frontend/progress.md` §2 별도 지침 또는 §3 변경 이력에 "페이지 추가"를 한 줄 기록(라우터 도입처럼 *지침* 수준이면 §2, 일상 페이지 추가는 §3에 *지침 추가* 행).
4. 인증 가드가 필요한지 결정해 §3 라우터 트리에 반영.

## 8. 페이지 md 공통 항목

각 페이지 파일은 같은 뼈대를 따른다(server/db의 테이블 1파일 패턴과 동일한 의도):

1. **목적** — 이 페이지가 사용자에게 무엇을 주는가, product/UX 우선순위 어디에 닿는가
2. **진입 경로** — URL, 인증 필요 여부, 어디서 오는지
3. **레이아웃** — 영역 구분 (좌/중/우, 헤더 등)
4. **상태(state)** — 페이지 로컬 vs 전역 컨텍스트
5. **사용 API** — 메서드·경로·요청·응답 스키마(서버 권위 출처 링크)
6. **컴포넌트 분해** — 신규/재사용 구분
7. **인터랙션 (Happy Path)** — 순서대로 사용자 행동 → 시스템 반응
8. **상태(로딩/에러/빈)** — 세 경우 모두
9. **나가는 길** — 어떤 액션이 어떤 페이지로 이동시키는지
10. **열린 항목 / 향후** — 잠정 결정, DB Phase 2/3 의존 부분
